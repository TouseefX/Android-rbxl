GUI RENDERING, DISPLAY ORDER, ZINDEX, AND ZINDEXBEHAVIOR
============================================================

This document explains the ScreenGui, BasePlayerGui, and GuiLayerCollector code from the 2022 Studio + full PDB decompilation.

The code is decompiled, so some names, function arguments, and types are incorrect. The rendering conclusions below are based on the important function names, branches, sorting calls, dirty flags, and data structures.


1. HIGH-LEVEL RENDERING HIERARCHY
---------------------------------

The relevant class hierarchy is approximately:

    BasePlayerGui
        |
        +-- ScreenGui
                |
                +-- GuiLayerCollector
                        |
                        +-- GuiBase2d
                                |
                                +-- GuiBase / GuiObject descendants

The rendering process is approximately:

    BasePlayerGui
        sort ScreenGuis by DisplayOrder
        render each ScreenGui
            GuiLayerCollector builds the Z-order list
            GuiObjects are rendered through Adorn/GfxGui

There are two different ordering systems:

    DisplayOrder  = ordering between ScreenGui layers
    ZIndex        = ordering between GUI objects inside a layer

They are not the same property.


2. BASEPLAYERGUI AND DISPLAYORDER
---------------------------------

The relevant functions are:

    BasePlayerGui::descendantDisplayOrderChanged
    BasePlayerGui::doRebuildRenderAndInputLists
    BasePlayerGui::getOrderedChildList
    BasePlayerGui::render2d

When ScreenGui.DisplayOrder changes, ScreenGui calls:

    BasePlayerGui::descendantDisplayOrderChanged()

The decompiled function is essentially:

    void BasePlayerGui::descendantDisplayOrderChanged()
    {
        rebuildRenderAndInputLists = true;
    }

This does not immediately sort everything. It marks the lists dirty. The lists are rebuilt later when rendering or input processing needs them.

The rebuild function approximately does this:

    void BasePlayerGui::doRebuildRenderAndInputLists()
    {
        rebuildRenderAndInputLists = false;

        orderedChildList.clear();
        getChildList(this, orderedChildList);

        stable_sort(
            orderedChildList.begin(),
            orderedChildList.end(),
            DisplayOrderComparator()
        );
    }

Therefore, ScreenGuis are collected and sorted by a DisplayOrder comparator.

Example:

    ScreenGui A: DisplayOrder = 1
    ScreenGui B: DisplayOrder = 5

The entire layer belonging to ScreenGui B will normally be rendered above the layer belonging to ScreenGui A.

Conceptually:

    BasePlayerGui
        ScreenGui A, DisplayOrder 1
        ScreenGui B, DisplayOrder 5

becomes:

    render ScreenGui A first
    render ScreenGui B second

If later-rendered items appear on top, B appears above A.

The exact comparator may also consider special flags, such as CoreGui-related ordering and onTopOfCoreBlur. Therefore DisplayOrder may not be the only sorting key in every situation.


3. BASEPLAYERGUI RENDERING ENTRY POINT
--------------------------------------

BasePlayerGui::render2d starts by ensuring its lists are current:

    if (rebuildRenderAndInputLists)
        doRebuildRenderAndInputLists();

It then submits GUI/adornment items through an adornable collector:

    adornableCollector->render2dItems(adorn);

The decompiler output is very large because this function also handles debug UI, text services, and other rendering-related work. The important ordering step occurs before the draw calls.

The approximate flow is:

    BasePlayerGui::render2d
        check dirty render/input lists
        rebuild ScreenGui ordering if necessary
        render collected GUI/adornment items


4. SCREENGUI RENDERING
----------------------

ScreenGui inherits from GuiLayerCollector:

    ScreenGui::ScreenGui()
        calls GuiLayerCollector::GuiLayerCollector()

ScreenGui::render2dContext calls the base class:

    GuiLayerCollector::render2dContext(this, adorn, context)

Before that call, ScreenGui prepares the viewport and GUI insets. It may also begin screen-space batching:

    adorn->beginScreenSpaceBatching(true)
    GuiLayerCollector::render2dContext(...)
    adorn->endScreenSpaceBatching()

So ScreenGui is mainly responsible for screen-level details such as:

    viewport
    screen insets
    safe-area insets
    2D versus 3D GUI mode
    DisplayOrder property
    CoreGui-related behavior

The actual descendant Z-order processing is implemented by GuiLayerCollector.


5. GUI LAYER COLLECTOR ZINDEXBEHAVIOR
-------------------------------------

GuiLayerCollector has a field named:

    zIndexBehavior

It has getter and setter functions:

    GuiLayerCollector::getZIndexBehavior
    GuiLayerCollector::setZIndexBehavior

The getter simply returns the stored enum value:

    return (unsigned int)this->zIndexBehavior;

The setter is important:

    void GuiLayerCollector::setZIndexBehavior(ZIndexBehavior behavior)
    {
        if (this->zIndexBehavior != behavior)
        {
            this->zIndexBehavior = behavior;

            this->rebuildGuiVector = true;
            this->rebuildUIQuadTree = true;

            if (this->gfxGui != nullptr)
                GfxGui::markDirty(this->gfxGui);

            raisePropertyChanged("ZIndexBehavior");
        }
    }

This proves that changing ZIndexBehavior affects actual rendering data. It causes the GUI vector and UI quad tree to be rebuilt.

The two normal enum values are:

    Enum.ZIndexBehavior.Global
    Enum.ZIndexBehavior.Sibling

The constructor initializes the field to zero. In the Z-order code, enum value 1 takes the sibling path, while the other path uses the global loader. This strongly suggests:

    0 = Global
    1 = Sibling

The enum numeric values should ideally be confirmed from the enum descriptor, but this is consistent with the known Roblox enum.


6. THE LOADZVECTORS FUNCTION
----------------------------

The most important function is:

    GuiLayerCollector::loadZVectors

The function contains a profiler label:

    "Rebuild Z-order list"

This is direct evidence that the function creates the render ordering list.

The relevant logic is approximately:

    void GuiLayerCollector::loadZVectors()
    {
        if (!rebuildGuiVector)
            return;

        rebuildGuiVector = false;
        guiVector.clear();

        if (zIndexBehavior == Sibling)
        {
            loadDescendantsSiblingStructured(
                this,
                guiVector
            );
        }
        else
        {
            loadDescendantsGlobalStructured(
                this,
                guiVector
            );

            stable_sort(
                guiVector.begin(),
                guiVector.end(),
                CompareOnlyZIndex()
            );
        }

        assignRenderIndices();
    }

The decompiler shows two important loader functions:

    loadDescendantsSiblingStructured
    loadDescendantsGlobalStructured

These correspond directly to the two ZIndexBehavior modes.


7. GLOBAL ZINDEXBEHAVIOR
------------------------

The global path calls:

    loadDescendantsGlobalStructured(...)

Then it explicitly calls:

    std::stable_sort(..., CompareOnlyZIndex)

This means the GUI descendants are collected into a global vector and sorted by ZIndex.

Conceptual example:

    ScreenGui
        Frame A, ZIndex = 1
            Text A, ZIndex = 100
        Frame B, ZIndex = 2

In a global-style model, the flattened list may be ordered conceptually as:

    Frame A, ZIndex 1
    Frame B, ZIndex 2
    Text A, ZIndex 100

Therefore Text A can render above Frame B even though Text A is inside Frame A.

Important: The exact vector may contain additional internal structure and visibility conditions. The conclusion is that the global loader allows descendants to participate in a common ZIndex ordering.


8. SIBLING ZINDEXBEHAVIOR
-------------------------

The sibling path calls:

    loadDescendantsSiblingStructured(...)

Unlike the global path, the visible code does not show a separate final stable_sort immediately afterward. This strongly suggests that the sibling loader builds the hierarchy in the required sibling order itself.

Conceptually, it behaves like:

    sort children of each parent by ZIndex
    render each child branch
    recursively sort and render that child's children

Illustrative pseudocode:

    void loadSiblingTree(GuiBase* parent, vector<GuiBase>& output)
    {
        children = parent->children;

        stable_sort(
            children.begin(),
            children.end(),
            compareByZIndex
        );

        for (child : children)
        {
            output.push_back(child);
            loadSiblingTree(child, output);
        }
    }

In sibling mode, a deeply nested child generally does not simply escape its parent branch and compete globally with unrelated objects elsewhere in the tree.

This makes GUI components more self-contained.


9. COMPAREONLYZINDEX
--------------------

The global path explicitly uses:

    RBX::CompareOnlyZIndex

This comparator is likely comparing the ZIndex property of two GuiBase/GuiObject instances.

Conceptually:

    bool CompareOnlyZIndex(a, b)
    {
        return a->ZIndex < b->ZIndex;
    }

It may have tie-breaking behavior or decompiler-hidden details. Because the engine uses stable_sort, objects with equal ZIndex normally preserve their previous relative ordering.

That previous ordering may depend on hierarchy or insertion order.


10. GUIVECTOR AND RENDERINDEX
-----------------------------

The ordered list is stored in:

    guiVector

After the vector is built, the code assigns sequential render indices. Conceptually:

    int renderIndex = 0;

    for (guiBase : guiVector)
    {
        renderOrder[guiBase] = renderIndex;

        if (uiQuadTree != nullptr)
            uiQuadTree->insert(guiBase, renderIndex);

        renderIndex++;
    }

The actual decompiler output shows:

    UIQuadTree::insert(guiBase, renderIndex)

and a map named:

    renderOrder

This means each GUI object receives a position in the calculated Z-order list.

The render index is not necessarily the same numeric value as the Roblox ZIndex property. It is an internal position after all ordering rules have been applied.

Example:

    GuiObject A, ZIndex = 1 -> renderIndex 0
    GuiObject B, ZIndex = 1 -> renderIndex 1
    GuiObject C, ZIndex = 5 -> renderIndex 2

The renderIndex is the final engine ordering position, while ZIndex is an input to the ordering process.


11. UIQUADTREE AND INPUT ORDER
------------------------------

GuiLayerCollector also maintains a UIQuadTree.

The quad tree is primarily spatial. It helps find GUI objects that occupy a particular screen location.

However, each object is inserted with a renderIndex:

    UIQuadTree::insert(guiBase, renderIndex)

This allows input processing to distinguish overlapping GUI objects.

Conceptually:

    candidates = UIQuadTree.query(mousePosition)
    target = candidate with the highest/frontmost renderIndex

Therefore the same calculated ordering can affect both:

    visual draw order
    mouse/touch hit testing

The relevant dirty flags include:

    rebuildGuiVector
    rebuildUIQuadTree
    rebuildRenderAndInputLists

When ZIndexBehavior changes, both the GUI ordering vector and the quad tree are invalidated.

When ScreenGui.DisplayOrder changes, BasePlayerGui invalidates its render and input lists.


12. WHY STABLE_SORT IS USED
---------------------------

The code uses stable sorting for ScreenGui ordering and global GUI ordering.

Stable sorting means that when two objects compare equal, their existing relative order is preserved.

For example:

    A: ZIndex = 5
    B: ZIndex = 5

If A was already before B, a stable sort keeps:

    A before B

This prevents unnecessary flickering or unpredictable reordering when multiple GUI objects have equal ZIndex values.

The original order may come from:

    hierarchy traversal
    child insertion order
    object creation order
    previous ordered-list order

The exact tie-break behavior may be implemented inside the loader functions.


13. DIRTY-REBUILD MODEL
-----------------------

The engine avoids rebuilding all ordering data every frame unless needed.

Changing ZIndexBehavior does this:

    zIndexBehavior = newValue
    rebuildGuiVector = true
    rebuildUIQuadTree = true
    mark GfxGui dirty

Changing ScreenGui.DisplayOrder does this:

    displayOrder = newValue
    BasePlayerGui.rebuildRenderAndInputLists = true

Then, later:

    render or input processing sees the dirty flag
    the appropriate list is rebuilt
    the dirty flag is cleared

This is a lazy update system.


14. RENDERING PIPELINE SUMMARY
------------------------------

The full conceptual pipeline is:

    BasePlayerGui::render2d
        |
        | if dirty:
        |     doRebuildRenderAndInputLists
        |
        | order ScreenGuis using DisplayOrderComparator
        v
    ScreenGui::render2dContext
        |
        | calculate viewport and GUI insets
        | begin screen-space batching if enabled
        v
    GuiLayerCollector::render2dContext
        |
        | load/rebuild Z-order data
        v
    GuiLayerCollector::loadZVectors
        |
        +-- Global:
        |       loadDescendantsGlobalStructured
        |       stable_sort by CompareOnlyZIndex
        |
        +-- Sibling:
                loadDescendantsSiblingStructured
                preserve sibling hierarchy/order
        |
        v
    guiVector
        |
        | assign internal renderIndex
        | insert objects into UIQuadTree
        v
    GUI draw calls through Adorn/GfxGui
        |
        v
    graphics backend


15. RELATION TO THE PREVIOUS EQUATIONDISPLAY CODE
-------------------------------------------------

The earlier EquationDisplay code called:

    LegacyAdorn::text2d(...)

That class appears to generate a label and submit 2D text through an adornment renderer.

The ScreenGui/GuiLayerCollector code shown here is the normal GUI layer pipeline. Whether EquationDisplay follows normal ScreenGui ZIndexBehavior depends on where it is attached and which collector invokes it.

If EquationDisplay is inside the normal GUI tree, its final order may be assigned by GuiLayerCollector.

If it is rendered through a separate profiler/debug adornment path, it may instead follow adornment submission order or a separate overlay priority.

The EquationDisplay function itself did not contain an explicit ZIndex field. The ordering may therefore be supplied by its parent collector or by the adornment system.

To establish that connection, inspect:

    EquationDisplay callers
    LegacyAdorn::text2d
    GuiItem/GuiObject render functions
    IAdornableCollector::render2dItems


16. OTHER DEPTH AND ORDERING CONCEPTS
-------------------------------------

The ScreenGui code also contains concepts that are different from normal ZIndex:

    DisplayOrder
    alwaysOnTop
    depthOffset
    worldSortPosition
    GfxGui::setToWorldCFrame
    onTopOfCoreBlur

These should not be confused with GuiObject.ZIndex.

DisplayOrder:
    orders ScreenGui layers relative to other ScreenGuis.

ZIndex:
    orders GUI objects inside a layer.

ZIndexBehavior:
    controls whether the ZIndex relationship is global or sibling-structured.

alwaysOnTop:
    relates mainly to projected/world/VR GUI depth and occlusion behavior.

worldSortPosition:
    relates to sorting world-space GUI or adornments in 3D.

depthOffset:
    is a graphics/depth adjustment, not the ordinary Roblox GuiObject.ZIndex property.

onTopOfCoreBlur:
    is a special CoreGui/blur ordering property and can cause BasePlayerGui to rebuild display ordering.


17. MOST IMPORTANT FUNCTIONS TO REMEMBER
-----------------------------------------

BasePlayerGui:

    descendantDisplayOrderChanged
        Marks render/input lists dirty.

    doRebuildRenderAndInputLists
        Builds the child list and sorts it using DisplayOrder logic.

    getOrderedChildList
        Returns the ordered ScreenGui list.

    render2d
        Begins the BasePlayerGui 2D rendering process.

GuiLayerCollector:

    getZIndexBehavior
        Returns the current Global/Sibling behavior.

    setZIndexBehavior
        Changes behavior and invalidates ordering data.

    loadZVectors
        Rebuilds the internal Z-order list.

    render2dContext
        Performs collector-level rendering and uses the ordered GUI data.

    loadDescendantsGlobalStructured
        Builds the global descendant list.

    loadDescendantsSiblingStructured
        Builds the sibling-structured descendant list.

    CompareOnlyZIndex
        Comparator used by the global stable sort.

ScreenGui:

    setDisplayOrder
        Changes ordering between ScreenGui layers.

    render2dContext
        Sets viewport/insets and calls GuiLayerCollector rendering.

    updateViewport
        Updates the usable GUI viewport.


18. FINAL CONCLUSION
--------------------

The code shows a two-level rendering order:

    Level 1: ScreenGui.DisplayOrder
    Level 2: GuiObject.ZIndex interpreted through ZIndexBehavior

The actual ZIndex implementation is in GuiLayerCollector::loadZVectors.

Global behavior:

    collect descendants globally
    stable-sort by ZIndex
    assign render indices

Sibling behavior:

    preserve parent/sibling structure
    order children within their relevant branches
    assign the resulting render indices

The engine then uses the resulting ordered vector and renderIndex values for rendering and likely for overlapping GUI input selection.

The decompiled code does not show a literal GPU Z coordinate being written for every GUI object. Instead, the engine mostly creates an ordered draw list. In a 2D renderer, the position in that list is the effective visual Z-order.

In short:

    DisplayOrder chooses which ScreenGui layer comes first.
    ZIndexBehavior chooses how descendants are grouped.
    ZIndex orders objects in the chosen model.
    guiVector stores the result.
    renderIndex records the final internal position.
    Adorn/GfxGui submits the final drawing commands.


19. RENDER ELIGIBILITY: WHICH CONTAINERS ACTUALLY RENDER
---------------------------------------------------------

The previous sections explain ordering after GUI objects have entered the render pipeline. This section explains whether a container is eligible to render in the first place.

This distinction is important:

    Render ordering asks: which eligible object appears above another?
    Render eligibility asks: should this object be submitted at all?

An object can have a valid ZIndex and still not render if its parent layer is disabled, detached, non-renderable, or sent through a different rendering path.


20. BASEPLAYERGUI IS THE MAIN SCREEN-GUI CONTAINER
--------------------------------------------------

ScreenGui::onAncestorChanged walks through its parent chain looking for a BasePlayerGui:

    parent = this->parent;

    while (parent != nullptr)
    {
        if (parent is BasePlayerGui)
            renderable = true;

        parent = parent->parent;
    }

The important logic is approximately:

    bool renderable = findFirstAncestorOfType<BasePlayerGui>() != nullptr;

    if (renderable != this->renderable)
    {
        this->renderable = renderable;
        IAdornable::shouldRenderSetDirty();
    }

This means attaching or detaching a ScreenGui from the expected GUI container changes whether it participates in rendering.

The renderable flag is not ZIndex. It is an eligibility flag.

A ScreenGui under the appropriate BasePlayerGui can become renderable. A ScreenGui that is only created in memory, parented somewhere unrelated, or detached from the expected service hierarchy may not be rendered through the normal player GUI path.


21. GuiLayerCollector::hasRenderableAncestor
--------------------------------------------

GuiLayerCollector has a function named:

    hasRenderableAncestor

The decompiled logic checks for either a Workspace ancestor or a BasePlayerGui ancestor:

    if (findFirstAncestorOfType<Workspace>() != nullptr)
        return true;

    if (findFirstAncestorOfType<BasePlayerGui>() != nullptr)
        return true;

    return false;

This is an important container rule. GuiLayerCollector objects may be considered renderable when attached to one of the engine's recognized rendering roots.

The exact behavior depends on the derived class and rendering path:

    BasePlayerGui path:
        normal player-screen GUI rendering

    Workspace path:
        possible world/projected GUI or other 3D-related GUI rendering

Therefore, finding a GuiLayerCollector does not automatically mean it is a normal 2D ScreenGui. Its ancestor determines which rendering system can discover it.


22. ScreenGui::shouldRender2d
------------------------------

ScreenGui contains a function approximately equivalent to:

    bool ScreenGui::shouldRender2d()
    {
        return renderable && uiSizeConstraintIsValid;
    }

The decompiler represents the second condition through an internal field, so the exact field name is uncertain. The important conditions are:

    renderable must be enabled
    the required GUI sizing/rendering state must be valid

This function is a gate before normal 2D drawing. If it returns false, ZIndex sorting is irrelevant because the ScreenGui should not submit normal 2D content.


23. ScreenGui::process CHECKS enabled
-------------------------------------

Input processing has an explicit enabled check:

    if (this->enabled)
    {
        if (isUserGuiRenderIn3dEnabled(...))
            process3d(...);
        else
            GuiLayerCollector::process(...);
    }
    else
    {
        return NOT_MOUSE_OVER;
    }

This proves that enabled state affects input processing. It is also a strong indication that disabled ScreenGuis are not active UI layers, although the exact draw-side gate may be implemented through the collector/adornable path rather than this function.

Do not assume input eligibility and draw eligibility are implemented by exactly the same function. They are related but separate pipelines.


24. NORMAL 2D VERSUS 3D/PROJECTED GUI
--------------------------------------

ScreenGui chooses between multiple rendering paths.

Normal screen-space path:

    ScreenGui::render2dContext
        update viewport/insets
        GuiLayerCollector::render2dContext
        render descendants in screen space

3D/projected path:

    ScreenGui::render3dAdorn
        find CoreGuiService userGuiAdornee
        verify the adornee is a BasePart
        build projected GUI matrix
        configure GfxGui
        render projected GUI

The code checks:

    isUserGuiRenderIn3dEnabled(...)

When this is false, normal 2D rendering is used.

When this is true, the GUI may be attached to a BasePart or another 3D surface and rendered through a projected/world-space path.

This matters for unexpected graphics because a graphic may not be coming from the ordinary ScreenGui 2D list at all.


25. RENDER2DCONTEXT AND THE ADORNABLE COLLECTOR
-----------------------------------------------

BasePlayerGui::render2d eventually calls:

    IAdornableCollector::render2dItems(adorn)

This collector is a submission point for objects implementing the engine's adornable interface. It may contain more than ordinary Frame/TextLabel objects, depending on the registered collectors and render passes.

This creates an important diagnostic possibility:

    unexpected graphics may come from an IAdornable or debug/adornment object
    rather than from a normal GuiObject descendant

The earlier EquationDisplay code used a LegacyAdorn::text2d call. That means a text item may be submitted through an adornment renderer rather than being a regular Frame child whose draw call is obvious in the ScreenGui tree.

To identify the source of unexpected graphics, trace the calls into:

    IAdornableCollector::render2dItems
    Adorn::text2d
    LegacyAdorn::text2d
    GuiLayerCollector::render2dContext
    GfxGui draw-item submission


26. VIEWPORT AND INSET RULES
----------------------------

ScreenGui::updateViewport calculates the drawable viewport from:

    fullscreenViewport
    coreUIInset
    hardwareSafeAreaInset
    screenInsetsType
    deprecated IgnoreGuiInset state

Depending on the selected inset mode, the viewport may be:

    the full screen viewport
    reduced by Core UI insets
    reduced by hardware safe-area insets
    reduced by both

This controls where the GUI can draw. It does not choose ZIndex order.

A graphic can appear unexpectedly positioned or clipped because of viewport/inset calculations even when its ZIndex is correct.


27. GFXGUI AND ALWAYS-ON-TOP ARE SEPARATE FROM ZINDEX
------------------------------------------------------

In the 3D path, ScreenGui configures GfxGui with values such as:

    setToWorldCFrame(...)
    alwaysOnTop = true
    lightInfluence = 0.0
    depthOffset = ...

These values control world-space/projected graphics and depth behavior. They are not ordinary GuiObject.ZIndex values.

In particular:

    alwaysOnTop = true

can cause a projected GUI to remain visible above 3D world geometry. It does not necessarily mean that the object is above every normal 2D ScreenGui.

Likewise:

    depthOffset
    worldSortPosition
    worldNormal

are graphics/depth fields for the GfxGui path, not proof of a ScreenGui ZIndex assignment.


28. SERVICE/CONTAINER ELIGIBILITY MODEL
----------------------------------------

Based on the supplied code, the rendering system can be summarized as follows:

    1. The object must be attached to a recognized rendering hierarchy.

       Normal ScreenGui:
           ancestor is BasePlayerGui

       Some world/projected GUI paths:
           recognized Workspace/3D ancestry or a valid user GUI adornee

    2. The ScreenGui must be renderable.

       ScreenGui::onAncestorChanged updates renderable.

    3. The relevant rendering mode must be active.

       Normal screen-space mode:
           ScreenGui::render2dContext

       User GUI in 3D mode:
           ScreenGui::render3dAdorn / updateGfxGui

    4. The GUI must pass enabled/visibility/size and related collector gates.

    5. The container must be submitted to the appropriate collector.

       BasePlayerGui uses IAdornableCollector::render2dItems.

    6. Only after eligibility is established are DisplayOrder and ZIndex ordering relevant.


29. WHY THIS DOES NOT YET EXPLAIN THE SPECIFIC TIX GRAPHICS
-----------------------------------------------------------

The supplied ScreenGui, BasePlayerGui, and GuiLayerCollector files explain the generic rendering framework, but they do not identify a class or object named TIX.

They show how an eligible GUI is ordered and submitted. They do not show which particular service creates the unexpected TIX graphic.

To identify that source, search the binary/decompiler output for:

    TIX
    tix
    the visible text of the graphic
    EquationDisplay
    ProfilerAdorn
    LegacyAdorn
    IAdornableCollector
    GfxGui
    DebugShowFlagState
    CoreGuiService
    BasePlayerGui

Then trace:

    creation of the object
    parent assignment
    registration with an adornable collector
    render2d/render2dContext call
    text2d or draw-item submission

If the TIX graphic is text, EquationDisplay or a profiler/debug adornment is a possible path. If it is a panel or visual overlay, it may be a normal GuiObject, CoreGui object, plugin UI, or a GfxGui/world-space object.

The current files establish the rules for whether and how objects render, but the creator of the specific TIX object must be found separately.


30. DIAGNOSTIC CHECKLIST FOR AN UNEXPECTED GRAPHIC
--------------------------------------------------

When a graphic appears unexpectedly, ask these questions in order:

    A. What class created it?
       Search constructor, factory, or make_shared calls.

    B. Where is it parented?
       BasePlayerGui, CoreGui, Workspace, plugin container, or nowhere visible?

    C. Which rendering path does it use?
       GuiLayerCollector, IAdornableCollector, LegacyAdorn, or GfxGui?

    D. Does it have renderable ancestry?
       BasePlayerGui/Workspace checks are important.

    E. Is the containing ScreenGui enabled and renderable?

    F. Is the GUI rendered in screen space or 3D/projected space?

    G. What ScreenGui.DisplayOrder does its layer have?

    H. What ZIndexBehavior and ZIndex values apply?

    I. Is alwaysOnTop, depthOffset, or CoreGui blur ordering involved?

    J. Is it a debug/profiler/adornment overlay outside the normal GUI tree?

Only questions G and H concern ordinary ZIndex ordering. Questions A through F determine why the object exists and enters a rendering path at all.


31. UPDATED BOTTOM LINE
-----------------------

The supplied code supports this complete distinction:

    CONTAINER ELIGIBILITY
        BasePlayerGui/Workspace ancestry
        ScreenGui::renderable
        enabled and rendering-mode checks
        viewport and 2D/3D path selection
        adornable/GfxGui registration

    LAYER ORDERING
        BasePlayerGui sorts ScreenGuis using DisplayOrder

    OBJECT ORDERING
        GuiLayerCollector applies Global or Sibling ZIndexBehavior
        Global mode flattens and stable-sorts by ZIndex
        Sibling mode preserves sibling hierarchy

    FINAL SUBMISSION
        guiVector and renderIndex feed collectors, quad trees, Adorn, and GfxGui

Therefore, a ZIndex explanation alone cannot identify every unexpected graphic. The graphic may be coming from a different eligible container or adornment path before ZIndex ordering is even applied.
